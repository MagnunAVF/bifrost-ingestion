# M2: Intelligent decision engine (v0.2.0)

## Goal

Keep the M1 math for clear-cut cases and send the ambiguous ones to a Python LangChain agent. The
agent decides with a local LLM, using tools that the Go pipeline exposes over MCP. M1's main known
limit goes away: cross-language duplicates such as the Portuguese entries 57 and 64 are no longer
inserted as new products. Everything still runs on the Apple M1 with 8 GB RAM, with no HTTP
server of our own (that is M3).

## Exit criteria

- [ ] `bifrost mcp` serves MCP over stdio. The tools in docs/mcp-tools.md pass Go tests that
      drive a real client session; logs go to stderr only
- [ ] Every tool declares its criticality (`read`, `write`, `critical`) in `_meta` and in its
      MCP annotations. The server enforces `--max-criticality`: tools above the cap are neither
      listed nor callable. Writes default to `dry_run`, require a `reason`, and are logged.
      Tests prove each guard: a capped-out call is refused, a dry run writes nothing, and a
      repeated write is a no-op
- [ ] The agent in agent/ returns a schema-validated decision (link to a Product id, insert, or
      reject) with a reason. Unit tests use a fake chat model and a fake MCP session
- [ ] `bifrost ingest` triages each entry:
      - at or above the upper bound → link
      - below the lower bound → insert
      - in between → the agent decides
- [ ] The run report adds `escalated` plus each escalation's decision and reason. With the agent
      stubbed out, `make check` covers every triage path, including agent timeout and crash
      (fallback as decided)
- [ ] On the fixture with real Ollama (`make e2e`), entries 57 and 64 link to their catalog
      products; no distinct catalog pair links; re-running creates nothing new; `--dry-run`
      counts equal the real run's
- [ ] `make check` runs Go and Python (ruff, mypy --strict, pytest) without Ollama or an LLM, and
      CI is green
- [ ] docs/architecture.md, the README and the ADRs describe the hybrid flow, with peak RSS and
      per-escalation latency measured on the M1

## Risks

- **Memory:** nomic-embed-text, a chat LLM, Go and Python at once can exhaust 8 GB.
  → Pick a small model (open question 2), measure peak RSS in 2.2, keep prompts short.
- **Model quality:** a small model may call tools or follow the schema unreliably.
  → Structured output validated with pydantic, temperature 0, retry once, then fall back.
  → Measure the model on the 57/64 pairs and on the closest distinct catalog pairs before 2.3.
- **Wrong links:** the agent may approve links it shouldn't.
  → Precision first, as in M1: a narrow band, and labelled pairs in 2.3. ADR 0002's negatives
  (max distinct pair 0.970) must stay unlinked.
- **Unsafe writes:** an agent with write tools can be steered by a crafted product name (prompt
  injection; the fixture already holds a SQLi payload) or can make a wrong write.
  → MCP annotations are hints a client may ignore, so Go enforces the criticality cap.
  → Writes default to dry run, are idempotent, have no destructive tools, and never apply
  flagged input.
  → Entry text is passed to the model as quoted data, never as instructions.
- **Process boundary:** spawning, hanging or crashing between Go and Python.
  → Per-call timeouts, a documented fallback (open question 5), and failures counted in the
  report, never a silent link.
- **Stdout:** MCP over stdio owns stdout, so one stray log line breaks the session.
  → stderr-only logging, plus a test in 2.1 that fails if a tool call prints to stdout.
- **Dependencies:** new ones on both sides (Go MCP SDK, LangChain, MCP adapters, pydantic).
  → Each needs approval (Rules); govulncheck and pip-audit run in `make check`.
- **Runtime:** each escalation costs a chat-model call of seconds, not milliseconds. On the
  fixture, the band holds few entries: the lowest M1 link is 0.984, and only the 2 inserted
  entries are known to fall below 0.975.
  → Count escalations and measure in 2.3; batching is M4.

## Open questions

Answer 1, 2, 6 and 7 in 2.0, and 4-5 in 2.3. Question 3 is answered (Decisions).

1. Process topology: does `bifrost ingest` spawn the agent, which in turn spawns `bifrost mcp`
   for its tools? Or does the agent drive the run? Either way, stdio only, no HTTP server.
2. Which chat model runs the agent on 8 GB with Ollama (e.g. a 3–4B instruct model), and is its
   tool calling reliable enough?
3. ~~Do the MCP tools stay read-only, or does the agent write through MCP?~~ Both: read and
   write tools, each with a criticality level the server enforces (Decisions, 2026-10-03).
4. Where is the band? The architecture suggests ~0.94-0.975. M1 measured the lowest known
   duplicate at 0.951 and the highest distinct pair at 0.970 (ADR 0002). Is the band calibrated
   on those pairs only, or on more labelled pairs (M1 open question 7)?
5. Fallback when the agent is unavailable or times out: apply the M1 rule (0.975 threshold),
   report as `deferred` with no write, or fail the record (exit 3)?
6. Which Go MCP SDK: the official github.com/modelcontextprotocol/go-sdk, or another? It's a new
   dependency.
7. Is the agent's reason stored in the database (an audit or proposals table, ADR 0003) or only
   in the run report?

## Decisions

- 2026-10-03: The Python agent lives in agent/ at the repo root as its own uv project (Python
  3.13 pinned in agent/.python-version, uv.lock committed). Tooling: ruff (lint and format), mypy
  --strict, pytest. Go stays at the root; one repo, one `make check`.
- 2026-10-03: Python never opens catalog.db; it reaches the catalog only through the
  `bifrost mcp` tools. internal/catalog stays the only code that touches SQLite.
- 2026-10-03: MCP transport is stdio only in M2. Network transports and any HTTP server are M3.
- 2026-10-03: M2 issues are ENG-8..ENG-12 (GitHub 21-25), with a new `agent` label for LLM
  agent and MCP work. The docs issue stays separate (ENG-12), as ENG-7 was in M1.
- 2026-10-03: The MCP tool contract (docs/mcp-tools.md) is written in 2.0, so that 2.1 (Go) and
  2.2 (Python) run in parallel lanes with no shared files.
- 2026-10-03: `bifrost mcp` exposes read and write tools (open question 3), and each tool has a
  criticality level:
  - `read`: no side effects (e.g. product lookup, nearest neighbours, seller link lookup).
  - `write`: additive and idempotent on the key (SellerName, Id) (e.g. link a seller entry to
    an existing Product).
  - `critical`: creates or changes catalog data (insert a Product and link it; fill a
    product's missing attributes).
  - No destructive tools in M2: no delete, and no Name or overwrite update.
- 2026-10-03: Criticality is declared twice: in the MCP spec's tool annotations (`readOnlyHint`,
  `destructiveHint`, `idempotentHint`, `openWorldHint`: false) for clients, and as
  `bifrost/criticality` in the tool's `_meta`. Annotations are hints, so the Go server is the
  enforcer:
  - `--max-criticality read|write|critical` (default `read`) hides and refuses tools above the
    cap.
  - Every write takes `dry_run` (default true) and a required `reason`, runs in one catalog
    transaction, never applies flagged input, and logs tool, arguments, reason and outcome to
    stderr.
  - ADR 0007 in 2.0.
